## 1. 执行摘要

### 当前产品阶段判断

Battery Materials Agent 当前处于 **内部 PoC（概念验证）向受控试点过渡** 的阶段。系统架构完整、AI 能力可信度框架已初步建立、核心研发链路（项目→实验任务→样品）基本打通，但存在 **2 个 P0 阻断性问题**（设备台账与物料规格库创建功能完全不可用），导致数据治理链路断裂。

### 最值得保留的产品亮点

1. **AI 输出可信度框架**：候选材料生成接口完整返回 `confidence`（置信度）、`key_assumptions`（关键假设）、`evidence_sources`（证据来源）、`human_review_required`（人工复核标记），并附带顶层 `ai_meta`（模型版本、Agent 信息、复核计数）。该设计符合材料研发可审计原则，建议作为标准范式推广到所有 AI 输出场景。
2. **实验任务幂等保护**：通过 `idempotency_key` 防止重复提交，前端生成 UUID 作为幂等键，后端命中后返回 `duplicated: true`。该机制有效防止网络抖动或双击导致的重复订单。
3. **项目-任务-样品数据血缘**：实验任务创建时强制校验 `project_id` 归属，样品创建时支持自动带入 `order_id`，从机制上避免了孤儿数据。
4. **配方生成 AI 元信息**：配方生成返回基于真实信号计算的 `confidence`（物料主数据命中率 + 合规结果），假设与证据如实标注成本模型参数，合规未通过时强制标记人工复核。

### 最影响客户信任的 P0/P1 问题

| 编号 | 问题 | 影响 |
|------|------|------|
| P0-EQ | 设备台账创建功能完全不可用（FK 约束指向错误 schema） | 用户无法新增设备，设备管理模块形同虚设 |
| P0-MAT | 物料规格库创建功能完全不可设（同 FK 约束问题） | 用户无法新增物料，配方生成与物料关联断裂 |
| P1-FORM | 所有创建/编辑表单缺少 `:rules` 前端校验 | 用户填表后提交才知错误，试错成本高 |
| P1-TTIP | 多处禁用按钮无 tooltip 说明禁用原因 | 用户无法感知按钮为何不可用 |

### 建议整改策略

采取 **"先治本、后治表"** 策略：
1. **阶段 0（P0 止血）**：修复 FK 约束 schema 指向问题，恢复设备与物料创建功能（预计 1-2 天）
2. **阶段 1（主链路打通）**：补全前端表单校验 + 禁用按钮 tooltip（预计 3-5 天）
3. **阶段 2（治理与可信度）**：统一术语、优化空状态、完善错误处理（预计 5-7 天）

### 链路三：数据资产治理

**操作步骤**：
1. 查询属性字典（MDM properties）
2. 查询检测方法（MDM test_methods）
3. 查询单位（MDM units）
4. 尝试新增设备（验证设备台账）
5. 尝试新增物料（验证物料规格库）

**成功节点**：
- 属性/方法/单位查询 → 200（数据完整）
- 设备查询 → 200（返回 3 条既有设备）
- 物料查询 → 200（返回物料列表）

**失败节点**：
- 设备新增 → 500（FK 约束 `fk_equipment_category` 指向错误 schema）
- 物料新增 → 500（FK 约束 `fk_raw_materials_categ` 指向错误 schema）

**根因分析**：
数据库中存在 FK 约束：
- `experiment.equipment.category` → `classifications(code)`（同 schema 查找）
- `industrialization.raw_materials.category` → `classifications(code)`（同 schema 查找）

但 `classifications` 表实际位于 **`mdm` 架构**，而非 `experiment` 或 `industrialization` 架构。这导致：
1. 任何 category 值（包括空字符串）都无法通过 FK 约束验证
2. 设备与物料创建功能完全不可用

**当前业务成熟度**：数据治理能力严重受损，两个核心主数据对象的写入功能完全不可用。

## 5. 页面级深度问题清单

### [P0-EQ-001] 设备台账 - 创建功能完全不可用

- **优先级**：P0
- **问题类型**：数据 / 功能
- **位置**：`/equipment` 页面 → 新增设备抽屉 → 保存按钮
- **触发前提**：打开新增设备抽屉，填写任意数据，点击保存
- **复现步骤**：
  1. 进入 `/equipment` 页面
  2. 点击「新增设备」
  3. 填写设备名称（如"电化学工作站"）
  4. 选择类别（如"电化学"）
  5. 点击保存
- **预期表现**：设备创建成功，出现在设备列表中
- **实际表现**：HTTP 500，错误信息：`IntegrityError: (psycopg.errors.ForeignKeyViolation) insert or update on table "equipment" violates foreign key constraint "fk_equipment_category"`
- **用户影响**：设备台账完全无法新增，用户无法建立设备档案，实验无法关联设备
- **研发业务影响**：实验数据无法关联设备，导致数据血缘断裂，无法追溯"哪台设备做的实验"
- **根因假设**：FK 约束 `fk_equipment_category` 定义为 `FOREIGN KEY (category) REFERENCES classifications(code)`，在 `experiment` 架构中执行。但 `classifications` 表实际位于 `mdm` 架构。PostgreSQL 在解析无 schema 前缀的表引用时，默认在当前 schema（`experiment`）中查找，找不到则报 FK  violation。
- **整改建议**：
  - 方案 A（推荐）：修改 FK 约束为 `FOREIGN KEY (category) REFERENCES mdm.classifications(code)`，使用 schema 前缀
  - 方案 B：在 `experiment` 架构中创建 `classifications` 表的视图或同义词
  - 方案 C：移除 FK 约束，改为应用层校验（不推荐，失去数据库级保护）
- **涉及字段或控件**：`experiment.equipment.category` 列
- **前端修改点**：无
- **后端/数据修改点**：`experiment` 架构的 FK 约束定义，需执行 ALTER TABLE DDL
- **验收标准**：使用任意有效 category 值（包括空字符串）创建设备均成功
- **建议责任角色**：后端 / DBA
- **预计工作量**：S
- **依赖项与风险**：需执行 DDL 迁移，建议在低峰期操作

- **触发前提**：打开任意创建/编辑表单
- **复现步骤**：
  1. 打开样品管理「新建样品」抽屉
  2. 不填样品名称、数量、单位
  3. 点击保存
- **预期表现**：前端即时高亮缺失字段，阻止提交
- **实际表现**：表单无校验，提交到后端后返回错误（部分后端有校验，但用户体验差）
- **用户影响**：用户需完整填表后才能发现错误，试错成本高；部分字段无明确提示导致反复提交失败
- **研发业务影响**：错误数据可能进入后端（如果后端校验不完整），导致数据质量下降
- **根因假设**：`a-form` 未配置 `:rules` 属性，或 `a-form-item` 缺少 `name` 属性（Ant Design Vue 校验依赖 `name`）
- **整改建议**：
  - 为所有 `a-form` 添加 `:rules` 和 `:model` 属性
  - 为所有 `a-form-item` 添加 `name` 属性
  - 必填字段配置 `[{ required: true, message: '...', trigger: 'blur' }]`
  - 数值字段配置 `type: 'number'` + `min`/`max` 范围
  - 邮箱字段配置 `type: 'email'`
  - 唯一性字段（业务编号、设备编号）增加异步校验
- **涉及字段或控件**：所有表单输入框、选择器、数值输入
- **前端修改点**：所有包含 `a-form` 的 Vue 组件（40+ 文件）
- **后端/数据修改点**：无（后端校验已部分完成）
- **验收标准**：漏填必填字段时前端即时提示；非法数值提交前被阻止
- **建议责任角色**：前端 / 产品
- **预计工作量**：L
- **依赖项与风险**：需逐页面修改，工作量大但风险低

### [P1-TTIP-001] 全局 - 多处禁用按钮缺少 tooltip 说明

- **优先级**：P1
- **问题类型**：UX
- **位置**：多个页面的禁用操作按钮
- **触发前提**：找到任意禁用状态的操作按钮
- **复现步骤**：
  1. 进入实验工作台，找到非 PENDING_APPROVAL 状态的实验任务
  2. 观察「审批」按钮
- **预期表现**：悬停禁用按钮显示 tooltip 说明原因
- **实际表现**：按钮仅显示为浅灰色，无说明
- **用户影响**：用户无法理解按钮为何不可用，可能误以为系统故障
- **研发业务影响**：降低用户信任度，增加客服成本
- **根因假设**：按钮使用 `v-if` 隐藏或 `:disabled` 禁用，但未包裹 `a-tooltip`
- **整改建议**：
  - 将 `v-if` 隐藏改为 `:disabled` + `a-tooltip`（始终可见但禁用时显示原因）
  - 封装统一操作按钮组件支持 `disabledReason` 属性
  - 优先覆盖审批、录入数据、删除、编辑等高频操作
- **涉及字段或控件**：所有 `:disabled` 按钮
- **前端修改点**：CandidateWorkbench.vue、Projects.vue、Dashboard.vue、FormulaDesign.vue 等
- **后端/数据修改点**：无
- **验收标准**：悬停禁用按钮显示 tooltip 说明原因
- **建议责任角色**：前端 / UX
- **预计工作量**：M
- **依赖项与风险**：低风险，纯前端修改

### [P1-EMPTY-001] 全局 - 部分空状态缺少下一步行动引导

## 7. UI/UX 重构方案

### 重构目标与原则

当前产品已覆盖项目、候选设计、性质预测、合成路径、实验任务、样品、配方、物料、设备、MDM、知识资产和智能体等能力，但现有导航仍偏向技术模块罗列。建议采用“**以项目为主线、以任务为入口、以角色和权限收敛界面**”的信息架构：研发人员围绕项目推进候选、预测、实验和迭代；数据、AI 平台与系统运维能力作为受权限控制的支撑域。

重构后应避免把业务域、平台能力、数据治理和商业化运维并列为同一层级。一级导航控制在 5-6 项；低频、专业或仅限管理员使用的能力进入“管理中心”并按角色可见。AI 能力应优先嵌入研发任务流，只有智能体/平台管理员需要直接操作编排、连接器和调用治理。

### 推荐的信息架构与左侧菜单

**一级菜单（默认按角色和权限显示）**：

1. **工作台**：我的待办、继续工作、项目概览、预警提醒、快捷创建
2. **研发项目**：项目组合、项目空间、阶段与里程碑、候选设计、性质预测、合成路径、配方与工艺
3. **实验与样品**：实验任务、实验记录与结果、样品与批次、设备与校准、实验数据质量
4. **数据与知识**：技术情报、知识图谱、属性/单位/测试方法字典、主数据、数据审核与审计
5. **AI 助手**：研发助手、智能体运行记录、评估与人审；研究员在任务页直接调用，平台配置按权限进入
6. **管理中心**：用户与角色、系统设置、工具与连接器、智能编排、调用关系、预算/账单、控制平面

**菜单与现有能力的迁移规则**：

| 现有入口/能力 | 重构后位置 | 设计说明 |
|---|---|---|
| Dashboard | 工作台 | 从静态总览升级为“待办 + 继续工作 + 预警 + 快捷创建”的行动入口 |
| 项目管理、候选设计、性质预测、合成路径、实验闭环、配方与工艺 | 研发项目 | 以项目空间串联，减少跨菜单查找与上下文切换 |
| 实验工作台、实验数据、样品管理、设备台账 | 实验与样品 | 按实验执行对象组织；设备侧重可用性、校准与任务关联 |
| 数据质量 | 实验与样品 + 数据与知识 | 实验页处理录入完整性/异常；治理页处理审核、规则、血缘和审计 |
| 物料规格库 | 研发项目中的配方与工艺 + 数据与知识中的主数据 | 配方工程师可在上下文中选择/申请物料；主数据管理员负责建模、审批和维护 |
| 技术情报、知识图谱、属性字典、主数据治理 | 数据与知识 | 统一知识资产和数据治理入口，避免概念分散 |
| 智能体管理、智能编排、工具与连接器、调用关系、评估中心 | AI 助手 / 管理中心 | 日常使用放入 AI 助手；编排、连接器、调用治理仅管理员可见 |
| 用户管理、系统设置、预算看板、收益账单、控制平面、能力契约 | 管理中心 | 低频或平台/商业化能力，默认不向普通研发角色展示 |

### 项目空间与任务闭环

菜单重组不能替代流程整合。建议将“项目空间”作为研发主入口，每个项目默认展示阶段看板和对象关系：目标与约束 → 候选材料 → 预测/证据 → 合成路线 → 实验任务 → 样品/批次 → 结果与数据质量 → 迭代决策。

项目内每个对象页面必须提供关联对象、状态、责任人、证据来源、数据质量与下一步操作。例如，候选材料详情应可直接查看预测结果、合成路线、关联实验、产出样品、实验结果、AI 置信度和人工复核状态，并提供“创建实验任务”“发起复核”“进入下一轮迭代”等上下文操作。跨对象跳转应保持 project_id、candidate_id、order_id、sample_id 等上下文自动带入。

### 核心用户角色及首页差异

首页应从信息展示页升级为“待决策/待行动”工作台。不同角色看到的卡片、快捷操作、预警和默认列表应不同，但共用统一的项目、对象和数据血缘模型。

| 角色 | 首页重点 | 高频操作 | 首屏关键问题 |
|---|---|---|---|
| 研发总监 | 项目组合、阶段风险、预算使用、团队负载、关键审批 | 审批、资源调整、查看经营/研发报告 | 哪些项目偏离目标，是否需要调整资源或停止投入？ |
| 项目负责人 | 项目阶段、候选对比、实验排期、阻塞项、跨团队协同 | 推进里程碑、分派任务、发起评审 | 下一步应推进什么，当前卡在哪里？ |
| 材料研究员 | 我的候选、预测队列、合成路线、待复核结果、实验反馈 | 生成/筛选候选、查看预测、创建实验任务、复核 AI 结论 | 哪个候选最值得继续投入实验？ |
| 实验员 | 今日实验、样品状态、设备可用性与校准、待录入结果 | 执行任务、创建样品、录入结果、上报异常 | 今天做什么，设备和样品是否就绪？ |
| 配方工程师 | 配方版本、物料替代、成本、性能约束、工艺窗口 | 生成配方、成本估算、比较版本、申请新增物料 | 当前配方能否兼顾性能、成本和可制造性？ |
| 数据管理员 | 主数据变更、数据质量队列、待审核记录、审计异常 | 维护字典、审核数据、处理质量规则、查看血缘 | 哪些数据问题会影响模型或研发决策可信度？ |
| EHS/质量负责人 | 危化品与合规、实验异常、设备校准、偏差与整改 | 审核合规证据、处理异常、发起质量复核 | 是否存在安全、质量或合规风险？ |
| 平台管理员 | Agent 成本、调用失败、连接器健康度、权限与安全事件 | 配置连接器、管理编排、排查运行、管理权限 | 平台是否稳定、可控且成本在预算内？ |

### 权限与可见性规则

- 普通研发角色默认只见“工作台、研发项目、实验与样品、数据与知识、AI 助手”中与其职责有关的页面。
- “智能编排、工具与连接器、调用关系、控制平面、收益账单、能力契约”等能力仅对平台管理员、系统管理员或被授权的业务负责人显示。
- 预算数据采用最小必要可见原则：研发总监和项目负责人查看项目预算，平台管理员查看模型/API 用量，财务或商业化角色查看账单；其他用户默认不可见。
- 无权限时不应以“空数据”伪装，应返回明确的无权限页面，并提供返回工作台或申请权限的入口。

### 数据质量与主数据边界

为避免“数据质量”“主数据治理”入口重叠，应明确职责边界：

| 场景 | 推荐入口 | 责任角色 | 处理内容 |
|---|---|---|---|
| 实验录入缺失、格式错误、仪器结果异常 | 实验与样品 > 数据质量 | 实验员、研究员 | 完整性校验、范围校验、异常补录与说明 |
| 属性、单位、测试方法、材料分类、模板定义 | 数据与知识 > 主数据 | 数据管理员 | 建模、变更、版本和审批 |
| 数据审核、审计、血缘、质量规则配置 | 数据与知识 > 数据审核与审计 | 数据管理员、质量负责人 | 审核、规则维护、追溯和异常闭环 |
| 项目级数据完整性、决策可用性 | 项目空间 | 项目负责人、研发总监 | 判断是否满足阶段门禁和继续投资条件 |

### AI 助手的嵌入式设计

AI 不应只作为独立“智能体菜单”存在。研究员应能在候选设计页获取生成与解释建议，在预测页查看依据与不确定性，在实验记录页获得记录辅助、异常解释和下一步实验建议，在配方页进行约束条件下的方案比较。

所有 AI 输出必须沿用现有可信度框架：显示 `confidence`、关键假设、证据来源、模型/Agent 版本和 `human_review_required`；低置信度、证据不足或高风险结果必须引导人工复核。智能编排、工具连接、调用关系、成本和运行失败治理则归入管理中心，由平台管理员负责。

### 空状态、加载状态、失败状态、无权限状态设计

**空状态统一规范**：无数据时必须区分“可创建”“需先完成前置操作”“无权限”三种情形。可创建场景使用“图标 + 原因说明 + 主操作 + 可选刷新”；依赖前置对象时明确指出前置条件并提供跳转；无权限不得使用普通空状态。

```html
<a-empty>
  <template #image>
    <span class="empty-icon">📭</span>
  </template>
  <p class="empty-description">暂无实验任务</p>
  <a-button type="primary" @click="onCreate">创建实验任务</a-button>
  <a-button @click="onRefresh">刷新</a-button>
</a-empty>
```

**加载状态统一规范**：
- 表格：`a-spin` 包裹 + `loading` 属性，保留表头与列结构以减少页面跳动
- 卡片：使用 `a-skeleton`，骨架结构应接近真实内容
- 按钮：使用 `loading` 属性，并在提交期间防止重复点击
- AI/长任务：展示阶段、耗时、可取消性和降级/失败原因，不以无限转圈代替状态反馈

**失败状态统一规范**：
```html
<a-result status="error" title="加载失败" :sub-title="errorMessage">
  <template #extra>
    <a-button type="primary" @click="onRetry">重试</a-button>
  </template>
</a-result>
```

**无权限状态统一规范**：
```html
<a-result status="403" title="无权限" sub-title="您没有权限访问此页面">
  <template #extra>
    <a-button @click="onBack">返回工作台</a-button>
  </template>
</a-result>
```

### 全局状态色语义规范

| 状态 | 颜色 | Hex | 适用场景 |
|---|---|---|---|
| 成功/通过/启用/空闲 | 绿 | #52c41a | 已完成、已通过、启用、设备空闲 |
| 警告/待处理/待复核 | 橙 | #fa8c16 | 待审批、待复核、临期校准、质量预警 |
| 错误/失败/不通过/高风险 | 红 | #ff4d4f | 已失败、校验不通过、危险/有毒、阻断异常 |
| 信息/处理中/草稿 | 蓝 | #1890ff | 处理中、运行中、草稿、一般信息 |
| 默认/已取消/归档/未知 | 灰 | #d9d9d9 | 已取消、已归档、退役、未知 |

注：同一状态不得在不同页面使用不同颜色；“禁用”是控件交互状态，不应与“失败/有毒”等业务状态共用红色语义。

### 按钮层级规范

1. **主操作按钮**：`type="primary"`，每个操作区域最多 1 个，应对应当前任务的下一步关键动作。
2. **次操作按钮**：`type="default"` 或 `ghost`，用于保存草稿、导入、刷新、取消等。
3. **文字按钮**：`type="link"`，用于查看详情、低频辅助动作。
4. **危险按钮**：`danger`，仅用于删除、作废、清空等不可逆操作，必须二次确认。
5. **禁用按钮**：保留按钮可见性，使用 `:disabled="true"` 并以 `a-tooltip` 说明不可用原因和解除条件；不应无提示地隐藏关键操作。

### 表格、筛选、搜索、批量操作、详情抽屉与版本对比

**表格规范**：
- 默认显示 10 条/页，可选 10/20/50/100；支持服务端分页。
- 支持列排序和列显隐配置；数据密集页默认突出名称、状态、关键指标、责任人、更新时间，次要列按需展开。
- 长文本使用 `ellipsis: true` + tooltip；数值列采用 `className: 'tabular-nums'`，单位与数值分层显示。
- 操作列固定右侧；涉及对象详情时优先支持“新页面/抽屉”两种查看方式。

**筛选与搜索规范**：
- 筛选区置于表格上方，使用 `a-form layout="inline"`；高频筛选默认展开，低频条件置于“更多筛选”。
- 筛选变化后 debounce 300ms 自动刷新，并显示已生效条件标签；提供“一键重置”。
- 项目内搜索默认限定当前项目；全局搜索应展示对象类型、项目归属与关键词高亮。

**批量操作规范**：
- 选中行后显示批量操作栏，只提供对当前对象状态合法的动作。
- 删除、作废、批量审批等高风险操作必须 `a-popconfirm`，展示影响数量与不可逆提示。
- 操作完成后反馈成功/失败数量，并可查看失败原因和逐条重试。

**详情抽屉与版本对比规范**：
- 详情使用 `a-drawer`，宽度 600-900px；有未保存修改时关闭需确认，支持 ESC 关闭。
- 对实验任务、配方、主数据等需要版本控制的对象，详情页提供版本历史、差异对比、操作者、时间和回滚/复制为新版本操作。
- 抽屉内优先展示与当前对象直接相关的血缘、证据、质量状态和下一步操作，避免成为单纯字段堆叠。

### 分阶段落地建议

1. **P0：项目工作台与角色首页**。先建立“我的待办、继续工作、预警、项目阶段看板、跨对象跳转”，验证研发人员能否更快完成主任务。
2. **P1：菜单收敛与权限治理**。按新一级菜单迁移页面；将控制平面、账单、连接器、编排等低频能力迁入管理中心并按权限隐藏。
3. **P1：数据质量边界与上下文操作**。区分实验录入质量、主数据治理和审核审计；在候选、实验、样品和配方页补齐关联对象与下一步动作。
4. **P2：嵌入式 AI 与可观测性**。在研发任务页嵌入 AI 建议与人工复核，补充运行记录、失败原因、成本与连接器治理。
5. **P2：统一基础交互**。在完成表单校验、禁用原因 tooltip、空状态行动引导、术语统一及数据密集页信息层级优化后，再开展全量视觉重构。

### 禁止使用的视觉模式

1. 禁止使用渐变背景作为主色调

5. 禁止空状态仅显示纯文本，无操作引导
6. 禁止禁用按钮无原因说明

## 9. 数据模型与系统能力整改

### 核心对象关系

```
项目 (projects)
  → 研发目标 (target_properties)
  → 候选材料 (candidates)
  → 预测/计算任务 (prediction_tasks)
  → 合成或制备方案 (synthesis_routes)

  → 批次 (batch_number)
```

| 实验数据 | result_id | qc_status (valid/invalid/requires_review) | — | test_method, operator | created_at, equipment_id |

### 必须建立的外键或关联关系

1. `experiment_orders.project_id` → `projects.project_id`（已建立）
2. `samples.source_order_id` → `experiment_orders.order_id`（已建立）
3. `samples.source_candidate_id` → `candidates.candidate_id`（已建立）
4. `experiment_result_records.sample_id` → `samples.sample_id`（已建立）
5. `experiment_result_records.equipment_id` → `equipment.equipment_id`（已建立）
6. `equipment.category` → `mdm.classifications.code`（**已建立但 schema 错误，需修复**）
7. `raw_materials.category` → `mdm.classifications.code`（**已建立但 schema 错误，需修复**）

### 必须禁止的删除与修改行为

1. 禁止删除已有下游实验任务的项目（应先归档）
2. 禁止删除已有实验结果的样品（应先删除结果）
3. 禁止修改已审批实验任务的 project_id（防止数据血缘断裂）
4. 禁止修改已关联实验数据的设备编号
5. 禁止删除已有配方版本的物料规格

### 去重和幂等规则

1. 项目名称：唯一约束，重复时返回 409（已实现）
2. 实验任务：支持 `idempotency_key` 幂等提交（已实现）
3. 样品业务编号：唯一约束，留空自动生成
4. 设备编号：唯一约束，留空自动生成
5. 物料编码：唯一约束，留空自动生成

### 统计口径统一方案

1. 项目进度：按任务完成数 / 总任务数计算
2. 候选材料数量：按 project_id + candidate_type 分组统计
3. 实验数据数量：按 order_id + sample_id 分组统计
4. 设备利用率：in_use 状态设备数 / 总设备数
5. 物料库存：按 material_id 分组，汇总 inventory_kg

### 数据质量规则

1. 离子电导率：范围 10⁻¹² ~ 10⁰ S/cm，超出范围标记异常
2. 温度：范围 -273 ~ 10000 °C，低于绝对零度拒绝
3. 浓度：≥0，负值拒绝
4. 纯度：0-100%，超出范围拒绝
5. 日期：结束日期不早于开始日期

### 数据血缘和可追溯性方案

1. 正向追溯：项目 → 实验任务 → 样品 → 实验数据 → 分析结果
2. 反向追溯：实验结果 → 样品 → 实验任务 → 项目
3. AI 证据追溯：候选材料 → ECML 运行记录 → 模型版本 + 提示词版本
4. 审计日志：所有创建/修改/删除操作记录操作人、时间、前后值

### AI 输出的版本、证据、置信度和人工审核机制

1. **版本**：每次 AI 生成关联 ECML 运行 ID，可追溯到具体模型版本
2. **证据**：`evidence_sources` 字段记录文献规律、数据库检索结果等
3. **置信度**：`confidence` 字段 0-1，三档配色（≥0.8 绿、0.5-0.8 橙、<0.5 红）
4. **人工审核**：`human_review_required` 标记，低置信度或检索未验证时强制复核
5. **审核记录**：人工复核后记录审核人、审核时间、审核结论

## 13. 最终结论

### 系统现在能否让真实新材料研发团队日常使用

**部分可用，但存在阻断性障碍。** 核心研发链路（项目→实验任务→样品）已基本打通，AI 生成与配方生成功能可用。但设备台账与物料规格库的创建功能完全不可用，导致实验无法关联设备、配方无法扩展物料库。在修复 P0 问题前，**不适合真实团队日常使用**。

### 适合内部 PoC、受控试点还是正式商业交付

**适合内部 PoC 和受控试点（需先修复 P0 问题）。** 修复 P0 问题后，系统可作为受控试点部署给 1-2 个研发团队试用。在当前状态下，不建议正式商业交付。

### 最应优先投入的 10 项整改

1. **修复设备创建 FK 约束**（P0，1-2 天）— 恢复设备台账写入功能
2. **修复物料创建 FK 约束**（P0，1-2 天）— 恢复物料规格库写入功能
3. **补全前端表单校验**（P1，3-5 天）— 消除用户操作障碍
4. **禁用按钮增加 tooltip**（P1，3-5 天）— 提升用户感知
5. **空状态增加操作按钮**（P1，3-5 天）— 引导用户下一步
6. **统一术语词表**（P2，5-7 天）— 消除歧义
7. **英文枚举值中文化**（P2，2-3 天）— 提升专业感
8. **实现数据删除保护**（P2，5-7 天）— 防止数据血缘断裂
9. **推广 ai_meta 到所有 AI 输出**（P2，3-5 天）— 统一可信度框架
10. **视觉体系重构**（P3，7-10 天）— 提升专业感和一致性

### 哪些功能建议保留并深化
